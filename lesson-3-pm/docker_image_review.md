# Технічний PM-review Docker-рішення

**Мета:** перевірити, що delivery-артефакти команди відповідають задачі `ai_ml_team_task.md` і критеріям `acceptance_criteria.md`. AI PM не переписує Dockerfile, а перевіряє, чи образ містить усе необхідне для запуску без ручного налаштування, і ставить питання там, де evidence немає.

**Як користуватися:** для кожного пункту фіксується статус і evidence. Статуси: ✅ OK · ⚠️ Є зауваження · ❌ Не виконано · ⬜ Не перевірено (артефакт ще не надано).

**Поточний стан (12.10.2026):** review підготовлено до отримання артефактів від команди; усі пункти мають статус ⬜. Після передачі артефактів review проводиться разом з DevOps і QA.

## 4.1 Dockerfile

| # | Перевірка | Як перевірити | На що дивиться AI PM (red flags) | Статус |
|---|---|---|---|---|
| 1.1 | Є окремі `Dockerfile.fat` і `Dockerfile.slim` | `ls Dockerfile.*` | Один Dockerfile з умовами або «slim зробимо потім» | ⬜ |
| 1.2 | Правильно вибрані base images | `grep ^FROM Dockerfile.*` | Fat — `python:3.13`, slim (фінальний stage) — `python:3.13-slim`. Red flag: `latest`, `python:3` без мінорної версії, інша версія Python у slim | ⬜ |
| 1.3 | Multi-stage build для slim | `grep -n "FROM\|COPY --from" Dockerfile.slim` | ≥ 2 stage; у фінальний копіюється лише встановлене середовище + код + модель. Red flag: другий `FROM` є, але в нього копіюється все (`COPY --from=builder / /`) | ⬜ |
| 1.4 | Логічний порядок COPY | Читання Dockerfile | Спочатку `COPY requirements.txt` → `pip install`, потім `COPY app/` і `model/`. Так зміна коду не перевстановлює torch і CI швидший. Red flag: `COPY . .` на початку | ⬜ |
| 1.5 | Використовується `.dockerignore` | `cat .dockerignore` | Виключені `.git`, `__pycache__`, `*.ipynb`, `data/`, `.env`, `venv/`, `tests/` (для runtime). Red flag: файлу немає або він порожній | ⬜ |
| 1.6 | Зрозуміла команда запуску | `grep -n "ENTRYPOINT\|CMD" Dockerfile.*` | `ENTRYPOINT ["python", "/app/inference.py"]` — однаковий у fat і slim | ⬜ |
| 1.7 | Non-root користувач у slim | `grep USER Dockerfile.slim` | Рекомендовано; якщо немає — фіксується як security-зауваження, не блокер для локального етапу | ⬜ |
| 1.8 | Base image зафіксований | Читання `FROM` | Бажано pin за digest (`python:3.13-slim@sha256:...`) для відтворюваності; без digest — ⚠️, не блокер | ⬜ |

## 4.2 Залежності

| # | Перевірка | Як перевірити | Red flags | Статус |
|---|---|---|---|---|
| 2.1 | Є `requirements.txt` | `cat requirements.txt` | Залежності встановлюються «вручну» в Dockerfile рядком `pip install torch torchvision` | ⬜ |
| 2.2 | Зафіксовані версії | Кожен рядок містить `==` | `torch`, `torch>=2.0`, `numpy` без версії | ⬜ |
| 2.3 | Сумісність із Python 3.13 | Команда підтверджує в README; збірка на 3.13 проходить | Версії torch/torchvision/pillow без wheels для 3.13 → pip намагається збирати з вихідників, збірка падає або тягне компілятори в slim | ⬜ |
| 2.4 | Немає зайвих бібліотек | Порівняти `requirements.txt` з імпортами в `inference.py` | `pandas`, `matplotlib`, `jupyter`, `scikit-learn`, `opencv` при тому, що inference їх не імпортує | ⬜ |
| 2.5 | Dev-залежності не в runtime image | `docker run --rm --entrypoint pip ml-infer-slim:1.0 list` | `pytest`, `black`, `ipykernel`, `jupyter` у slim. Якщо dev-залежності потрібні — окремий `requirements-dev.txt` | ⬜ |
| 2.6 | Однакова збірка torch у fat і slim | `pip show torch` в обох образах | Fat з CUDA-wheel (+2 ГБ), slim з CPU-wheel → «оптимізація» насправді є зміною runtime і може змінити числа. Обидва мають бути CPU-only (для цього сценарію GPU не потрібен — уточнити) | ⬜ |
| 2.7 | Ліцензії | Перелік ліцензій ключових пакетів і ваг моделі | Ваги ImageNet-моделей torchvision мають власні умови використання — підтвердити для комерційного застосування | ⬜ |

## 4.3 Запуск inference

| # | Перевірка | Як перевірити | Red flags | Статус |
|---|---|---|---|---|
| 3.1 | Обидва образи збираються | `docker build --no-cache -f Dockerfile.fat -t ml-infer-fat:1.0 .` та аналогічно для slim, exit code 0 | Збирається лише з кешем на машині інженера | ⬜ |
| 3.2 | Обидва образи запускаються | `docker run --rm -v "$PWD/tests:/data:ro" ml-infer-fat:1.0 /data/test_image.jpg` і те саме для slim | Потрібно щось доустановити або змінити всередині контейнера | ⬜ |
| 3.3 | Можна передати test input | Шлях до зображення передається аргументом, файл монтується через volume | Шлях «зашитий» у код; працює лише з одним файлом | ⬜ |
| 3.4 | Повертається top-3 prediction | Вивід — валідний JSON із 3 класами + `model_version` | Повертається лише top-1, або вивід — «сирий» тензор/лог без структури | ⬜ |
| 3.5 | Зрозуміла обробка помилок | `docker run ... /data/missing.jpg`, `docker run ... /data/not_an_image.txt` | Traceback без пояснення або exit code 0 при помилці (CI не помітить збій) | ⬜ |
| 3.6 | Команди запуску описані в README | Холодний прогін за README людиною, яка не писала код | Команди в README відрізняються від реальних тегів/шляхів | ⬜ |

## 4.4 Відтворюваність

| # | Перевірка | Як перевірити | Red flags | Статус |
|---|---|---|---|---|
| 4.1 | Той самий model artifact | `docker run --rm --entrypoint sha256sum <image> /app/model/model.pt` для fat і slim — однаковий хеш, збігається з README | Різні хеші, або модель завантажується з інтернету при старті | ⬜ |
| 4.2 | Однаковий preprocessing | Той самий `inference.py` в обох образах (`sha256sum /app/inference.py`); transforms взяті з `weights.transforms()` | Різні версії коду в образах; ручний resize/normalize з іншими параметрами | ⬜ |
| 4.3 | Однаковий test input | Один файл `tests/test_image.jpg`, SHA-256 у README | Кожен інженер тестує «на своїй картинці» | ⬜ |
| 4.4 | Inference збігається | Порівняння JSON fat vs slim vs `tests/expected_output.json`: класи й порядок однакові, `|Δp| ≤ 1e-4` | Порівняння «на око» або тільки top-1 | ⬜ |
| 4.5 | Описана версія і джерело моделі | README: архітектура, `weights=IMAGENET1K_V1` (або інше), дата збереження, SHA-256; `model_version` у виводі | Невідомо, яка модель дала prediction | ⬜ |
| 4.6 | Модель працює без мережі | `docker run --network none ...` | Падає без інтернету → прихована залежність від зовнішнього ресурсу | ⬜ |
