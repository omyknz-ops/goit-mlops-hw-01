## 1. Бізнесовий контекст

Команда має модель класифікації зображень, яка сьогодні працює лише в середовищі ML-інженера. Бізнесу потрібно, щоб цю модель можна було однаково запустити на будь-якій машині: у колеги, у CI/CD-пайплайні, на staging, а згодом — у production. Поки модель існує як «файл, що працює на ноутбуці», її не можна ні протестувати незалежно, ні передати DevOps, ні показати замовнику. Контейнеризація прибирає клас проблем «працює тільки в мене» і робить реліз передбачуваним.

## 2. Яку модель контейнеризуємо

- **Тип задачі:** класифікація зображень (image → клас).
- **Джерело моделі:** pretrained-модель із `torchvision.models` (ImageNet-1K, 1000 класів). Робоча гіпотеза — ResNet-18 з вагами `IMAGENET1K_V1`; **фінальну архітектуру та ваги команда підтверджує письмово** (див. README → Questions to AI/ML Team).
- **Артефакт моделі:** `model/model.pt` — ваги, збережені в репозиторії (або в artifact storage) з версією та контрольною сумою SHA-256. Модель **не завантажується з інтернету під час запуску контейнера**: інакше inference залежить від мережі й не є відтворюваним.
- **Retraining не передбачений** — використовуємо модель «як є».

## 3. Для чого потрібен inference

Inference — це етап, на якому навчена модель отримує нове зображення й повертає передбачення. Для цього проєкту:

- **Вхід:** шлях до зображення (JPEG/PNG), переданий у контейнер через аргумент `docker run`.
- **Вихід:** top-3 prediction у JSON — `class_id`, `label`, `probability` для кожного з трьох класів + `model_version`.
- **Сценарій використання на цьому етапі:** CLI-запуск для перевірки (локально та в CI/CD). API-сервіс (`/predict`) — наступний етап, див. `compose_readiness_checklist.md`.

## 4. Чому Docker image — це delivery-артефакт

`ML-модель + inference-код + залежності + системне середовище = Docker image`

Саме образ, а не окремі файли, передається далі по ланцюжку: локальна збірка → registry → CI/CD → staging → production. Тому приймаємо не «код у репозиторії», а **зібраний образ із назвою та версією**, який запускається однією командою без ручного налаштування середовища.

## 5. Чому два варіанти образу: fat і slim

| Образ | База | Призначення |
|---|---|---|
| `ml-infer-fat:1.0` | `python:3.13` (повний Debian) | Перша перевірка: простий Dockerfile, мінімум ризику «щось забули». Слугує **еталоном коректності** inference. |
| `ml-infer-slim:1.0` | `python:3.13-slim`, **multi-stage build** | Оптимізований варіант для delivery: менший розмір, лише runtime-залежності, менша attack surface, швидший pull у staging. |

Логіка: спочатку доводимо, що модель працює (fat), потім оптимізуємо (slim) і доводимо, що оптимізація **нічого не зламала**. Без fat-еталону немає з чим порівнювати slim.

## 6. Ключовий принцип оптимізації

**Після оптимізації inference не має змінитися.** На однаковому test input fat і slim повертають однакові top-3 класи в однаковому порядку; ймовірності збігаються з точністю до 1e-4 (критерій узгоджено в `acceptance_criteria.md`). Розмір, швидкість і security оцінюються лише після підтвердження коректності.

## 7. Де результат має бути придатний для перевірки

| Середовище | Що має бути можливо | Статус на цьому етапі |
|---|---|---|
| Локально | Будь-який член команди клонує репо, виконує команди з README, збирає і запускає обидва образи | **Обов'язково (Definition of Done)** |
| CI/CD | Збірка обох образів і порівняння inference на test input без ручних дій | Обов'язково — команди мають бути придатні до автоматизації |
| Staging | Slim image запушено в registry з версійним тегом, готовий до розгортання | Ціль наступного етапу; рішення — після `optimization_report_review.md` |

## 8. Межі проєкту

**In scope:** два Dockerfile, `.dockerignore`, зафіксований `requirements.txt`, inference-скрипт, README, `report.md` з порівнянням fat vs slim.
**Out of scope:** retraining, покращення accuracy, production Kubernetes, full monitoring.

## 9. Що вважаємо успіхом

Slim image збирається й запускається будь-ким із команди за інструкцією з README, дає той самий top-3 результат, що й fat, і має вимірювано менший розмір. Порівняння підтверджене цифрами в `report.md`, а не словами «оптимізовано».
